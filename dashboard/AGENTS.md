## Consistency comes first

Most of the work on this dashboard is bringing it back into line rather than
adding to it. A page that looks different from its siblings is a defect, even
when it works, so before drawing or restyling anything: find the screens that
already solve the same need, and follow them. When two places disagree, one of
them is wrong — fix the outlier instead of keeping both.

- Shared shapes live in `src/components/custom`, not in the pages that happen to need them first. A measure, a heading level, a field variant or a row that more than one screen draws belongs in the component all of them use.
- A rule that only lives on one screen will drift. If a page caps a field at a measure, the cap belongs in the component or the shared class, not in the page that needed it that day.
- Read the HeroUI docs and the demo closest to the need before composing. Where HeroUI already prescribes the anatomy — dialog sections, alert on a surface, the pending button — use it, and keep the library's defaults except where this file says otherwise.
- Every visual change is checked in a browser at a wide and a narrow width, in both themes and both locales, before it is called done. Several past fixes were only visible at one of those.

## Data loading (TanStack Query + Router)

- Pages read server data with `useSuspenseQuery`; never branch on `isPending`/`isLoading`/`isFetching`/`isError` inside a page. Loading falls back to the route's `pendingComponent`, errors to the route's error component.
- A suspense query's `data` is never `undefined`, but a nullable payload (e.g. an expired session returns `null`) is a real value: handle it as data, not as a loading state.
- Data a page needs at first paint is loaded in the route `loader` via `context.queryClient` (`ensureQueryData`, or `fetchQuery` when freshness must be enforced, e.g. the session check in `_protected`). Loaders already run on hover preloading (`defaultPreload: "intent"`).
- `useSuspenseQuery` supports neither `enabled` nor `placeholderData`; conditional fetching belongs in the loader.
- Express refetch behavior through query options (`refetchOnWindowFocus`, `staleTime`), not manual DOM listeners plus `refetchQueries`; duplicating both refetches twice.
- A query for the signed-in account's own data carries `meta: { requiresSession: true }`, which is how clearing the session finds them all: `clearSessionQueries` cancels and removes by that marker instead of naming every key. A new session-scoped query needs the marker, or a sign-out leaves its data cached.

## Routing and guards

- Routes are files under `src/routes`; the tree is generated into `routeTree.gen.ts` and never edited by hand. A route file exports `Route` from `createFileRoute` and the page component lives under `src/pages`.
- Each route declares what it needs at the route: a `loader` for first-paint data, `pendingComponent` for the wait, `errorComponent` for a failure, `validateSearch` for search-string state. Reference `Route.useSearch()` from the page rather than reading the location.
- The signed-in area hangs off `_protected`, whose loader refuses an anonymous session: it clears the session queries and throws `redirect({ to: "/login" })`. Loaders may throw a redirect; catch blocks around `router.navigate`/`router.invalidate` treat it as the intended outcome rather than an error.
- Tabs and other list selections live in the URL search string and nowhere else. `src/pages/console/tabs.ts` narrows an unknown search value onto the allowed ids, falls back to the first, and switching navigates with `replace: true` so the back button leaves the page instead of stepping through every tab.

## Forms

- Forms are TanStack Form through the hooks in `src/forms/use-app-form.ts`: `createFormHook` registers `FormField`, `OtpField`, `Form`, `FormError` and `SubmitButton`, and pages call `useAppForm` rather than composing HeroUI fields themselves.
- Field validation on blur, form validation on submit. Fields are disabled while the form submits, and a field's own server error is cleared as soon as the user edits it.
- Server errors reach the form through `src/forms/server-errors.ts`: a code or a `validation_failed` location maps to a field via a per-form `ServerFieldMap`, and anything unmapped becomes a form-level error. Do not print raw error codes; the message comes from `describeError`.
- `Form` stops duplicate submits itself, and after a failed submit moves focus to the first invalid field or the form's error summary. Keep `data-form-error-summary` on that summary so the focus target can be found.

## API layer

- Requests go through the single `client` in `src/api/client.ts` (openapi-fetch, same-origin credentials). It converts a failed response into an `ApiError` and an aborted request into an `AbortError`; a response with no body is not data, so reads return through `requireJsonData`.
- `src/api/errors.ts` is the only place that turns a failure into user-facing wording. Add a code to its table with translated text; keep `isCancellation` checks in catch paths so a cancelled request never surfaces as an error.
- `src/api/queries.ts` and `src/api/mutations.ts` hold query and mutation options; pages do not build request options inline. Generated declarations come from `mise run ci:api-types`; hand-written requests the generator does not cover belong in `src/api/raw-paths.ts`, which is intersected into the client's paths.

## Console structure

- The signed-in pages share one shell, `ConsoleLayout`: an instance identity block, a navigation list that names a section and its icon once, the account footer with sign-out, and a header that shows which instance and which section you are in. Mobile navigation is the same list inside a `Drawer`; the desktop rail collapses and stays put while the page scrolls. Add a section by adding one entry to the list in `ConsoleLayout`, not by drawing a nav of your own.
- The shell owns identity: the header supplies the document's single `h1` and names the section in view, and it reads the same section table the sidebar does, so a label is written once. A page does not repeat its own heading, and it does not describe what it is — the heading and the cards say that.
- Page content sits in one measured column (`max-w-4xl`) in `main`, which is also a container context (`@container`). The column carries the page's own padding, so a card does not add a top margin of its own. Every block keeps to that measure at every width, tables included; nothing bleeds back into the gutters.
- A block on a console page is a `ConsoleCard`: heading, then content capped at the card's measure, so every card on the console reads the same width including its notes and lists. Cards stack in one column at every width; side-by-side cards shared a row they had no use for.
- A tabbed page keeps the selected tab in the URL (see Routing), never wraps a tab label, and lines the tab strip up with the card below it. Tabs take the width of their labels rather than equal columns, so a five-tab strip still fits the measure.
- Nothing on a console page is collapsed. A tab that carries many independent actions is an `ItemList` with one row per action — its name, one line saying what it does, and its button — so every action is visible at once. An action that needs input opens that input in a dialog; one that needs none runs from the row, behind an `AlertDialog` when it cannot be undone. The one thing the user has not finished — the form establishing a missing factor — is drawn in place on a `ConsoleCard`, not behind a button.
- Lists come in two shapes, chosen by how they are read:
  - The management directory (users, user groups, invitations) is a `DataTable`. It runs to many rows and pages, and an admin compares one column down the rows — role, state, last sign-in — which is what column alignment is for. Keep its columns to what fits the measure; put row actions in the pinned column as icon buttons.
  - Everything the signed-in account owns (passkeys, sessions, identities, tokens, connected applications) and the per-account lists on an admin's user page are an `ItemList`. Those hold a handful of records read one at a time, so each row names the record, carries a muted line of details that name themselves ("Added …", "Last used …") instead of leaning on column headers, and keeps its actions at the trailing edge.
- List pages follow the same shape: the page's action first at the top left, followed by its search and filters, then the list over the page's query, with `TableEmptyState` for the empty case. Collect input in a dialog or a popover (the identity filter), not in a panel that expands under the toolbar.
- A list that is the page's whole subject stays on the page background: no `ConsoleCard` and no `ItemList` title, with the action row and any notice above it in a plain `flex flex-col gap-4` column. The console header already names it. A list that is one block among several — the four lists on an admin's Access tab — takes an `ItemList` `title`, which draws the heading inside the card.
- Panels on the same page go through the same `useAppForm` fields and the same list, empty state and dialog shapes; a panel that draws its own list, form or button row is the outlier to fix.

## Tables and lists

- Console tables come from `DataTable`, given one column definition per column (id, header, cell, `align`, `pinned`), a `rowId`, the rows, and an `empty` node. Cells and headers never wrap; a table wider than its column scrolls sideways instead of clipping. Dates in a table or a list show the day only; the time of day is noise at a glance.
- A trailing action column is marked `pinned` and renders through `TableActionCell` / `TableActionColumn`, which stick to the container's trailing edge so row actions stay reachable while the other columns scroll under them. The pinned cell paints its own opaque background; leave that to the component.
- While rows are still loading, `DataTable` stands in with one full-width spinner row on the console's gray surface, and `ItemList` with a spinner in its card. Do not branch on loading inside cell or row renderers.
- `ItemList` is one HeroUI `Card` with a rule between rows; `ItemListRow` takes `icon`, `title`, `badges` (chips for a state worth noticing, such as a role or "this device" — not for the ordinary state), `details`, `actions`, `link` for a row that opens the record, and `children` for a row's own error or note. On a narrow screen the details stack one to a line and a labelled action moves under the text. `footer` sits under the last row, for an action over the whole list such as ending every session.
- An action the account cannot take right now renders as a disabled button with the reason in a `Tooltip` on it, not as a sentence elsewhere on the page. Pass the disabled button as the child of `Tooltip.Trigger`, since a disabled button emits no hover or focus for the tooltip to answer, and use `delay={0}`.
- An irreversible row action goes through an `AlertDialog` that names what it removes.

## Components and surfaces

- Import HeroUI through the wrappers in `src/components/custom` when one exists: `Button`, `ConsoleCard`, `ItemList`, `SurfaceAlert`, `SecretReveal`, `TableActionCell`, `TableEmptyState`, `FormField`, `OtpField`. The wrappers exist so one place decides the pending spinner, the surface treatment, or the pinned cell, and every call site stays consistent.
- Every button in the app is `Button` from `src/components/custom/Button.tsx`, including `form.SubmitButton`. Mark work in flight with `isPending` and let the wrapper draw the spinner: a labelled button keeps its text beside it, an icon-only button swaps the icon for it. Do not put a `Spinner` inside a button, and do not swap the label yourself to signal pending.
- Pending work is shown on the control that started it, in the component the user is looking at; a page-level toast is for outcomes, not for progress.
- Anything drawn on a Card or a Dialog is on a surface: notices use `SurfaceAlert`, fields and text areas use `variant="secondary"`. A component that may be drawn either way takes the choice as a prop (`onSurface` on `SecretReveal` and `TotpSetup`), defaulting to the page background. A page-level notice — outside any card — is the library's own `Alert`.
- One-time codes go into `OtpField`, never a free-text box: digits by default, a passed `pattern`/`inputMode` for letter-bearing codes such as the pairing code, in HeroUI's `InputOTP` slots with a separator where the code is shown that way elsewhere.
- A dialog follows HeroUI's anatomy: `Modal.Header` for the title, `Modal.Body` for the content that scrolls, `Modal.Footer` for the actions, cancel on the left and the one that finishes on the right. The form element spans body and footer, so a long body scrolls under a footer that stays in place.
- A secret the server will not show again — recovery codes, a token's plaintext — is revealed in `SecretReveal`, on its own dialog for one step of a section and page-wide only when the flow is finished either way. The reveal gates its continue action on the saved confirmation, warns before leaving the page, and hides the canvas or field it cannot draw yet rather than unmounting it.
- A component that draws from asynchronous data keeps the element mounted and skips the value it does not have yet. Unmounting on an empty value loses the ref, and the later real value has nothing left to draw on.

## Layout and chrome

- The page's share of the viewport comes from the `--app-viewport-height`, `--app-sticky-offset` and gutter properties in `src/styles/index.css`. Full-height regions, sticky headers and rails use those properties instead of `100dvh` and `top-0`, so a development panel docked at an edge never hides the page; an undocked page reads the defaults. See Devtools for who writes them.
- A sticky region is pinned by an ancestor that does not scroll. An `overflow-hidden` wrapper is a scroll container, so sticking the aside inside it pins it to a box that never scrolls; the transition wrapper sticks and the aside fills it.
- A side rail ends with its own footer — the account row, the sign-out — inside a column that can shrink (`min-h-0` plus its own scroll area), otherwise a short viewport pushes the footer out of the rail and clips it.

## Devtools (development only)

- The TanStack Devtools shell and the API dock are mounted behind `import.meta.env.DEV` from `main.tsx`, beside the API mock, so none of it ships in the production bundle. Nothing under `src/devtools` may be imported by app code.
- The dock watches the shell's panel through the DOM and writes the page's share of the viewport on `<html>`. It is a watch rather than a devtools plugin because a plugin renders only while its own pane is open, and the page has to make room for whichever panel is open.
- Mock fixtures live with the mock, not in the components that read them, and the mock owns whole verbs: while reads are mocked every GET is answered, writes only when "Override writes" is on. The panel's rows edit one config object; a write updates that object so later reads agree with it.
- The mock covers the management area as well as the account pages, and the panel is the switchboard for a walkthrough: the **Session role** decides whether the management section appears in the sidebar and whether its pages answer or redirect home, and the **Management** counts decide how many accounts, user groups and invitations exist. The account directory pages by cursor, so its count goes well above what a single page holds — a walkthrough has to be able to reach the second page.
- The mock keeps the account it is signed in as in step with the directory's first row: editing that account's profile or role moves both, so the session the console reads and the record the admin list reads never disagree.
- A request with no fixture fails as `mock_unmocked` instead of reaching the server, so a page never draws half fabricated data and half real data. Passkey ceremonies fail that way, since a fabricated challenge cannot be answered.
- Mocked responses wait the configured delay before they answer, so the pending states a page draws while waiting stay visible during development. Keep that wait in the mock, and keep the panel's list sizes and delay capped by the exported maxima.
- The master switch returns to off after a reload, while the data edits, including the writes switch, persist: a console left serving fabricated data across reloads would hide the server it is being developed against.
