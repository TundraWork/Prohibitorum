## Consistency comes first

A page that looks different from its siblings is a defect, even
when it works, so before drawing or restyling anything: find the screens that
already solve the same need, and follow them. When two places disagree, one of
them is wrong — fix the outlier instead of keeping both.

- Shared shapes live in `src/components/custom`, not in the pages that happen to need them first. A measure, a heading level, a field variant or a row that more than one screen draws belongs in the component all of them use.
- A rule that only lives on one screen will drift. If a page caps a field at a measure, the cap belongs in the component or the shared class, not in the page that needed it that day.
- Compose from the coss components in `src/components/ui` and keep their defaults except where this file says otherwise; do not edit a vendored file to suit one screen.
- Every visual change is checked in a browser at a wide and a narrow width, in both themes and both locales, before it is called done.

## Data loading (TanStack Query + Router)

- Pages read server data with `useSuspenseQuery`; never branch on `isPending`/`isLoading`/`isFetching`/`isError` inside a page. Loading falls back to the route's `pendingComponent`, errors to the route's error component.
- A suspense query's `data` is never `undefined`, but a nullable payload (e.g. an expired session returns `null`) is a real value: handle it as data, not as a loading state.
- Data a page needs at first paint is loaded in the route `loader` via `context.queryClient` (`ensureQueryData`, or `fetchQuery` when freshness must be enforced, e.g. the session check in `_protected`). Loaders already run on hover preloading (`defaultPreload: "intent"`).
- `useSuspenseQuery` supports neither `enabled` nor `placeholderData`; conditional fetching belongs in the loader.
- Express refetch behavior through query options (`refetchOnWindowFocus`, `staleTime`), not manual DOM listeners plus `refetchQueries`; duplicating both refetches twice.
- A delete that removes the whole record and navigates away invalidates its families with `refetchType: "none"` (`invalidateAfterDelete` in `src/api/mutations.ts`), never with a plain `invalidateQueries`: the page that deleted the record is still mounted until its navigation runs, and a refetch of the record's own key would answer 404 and raise an error toast for something the reader just did. The list the page navigates to is not mounted yet and refetches when it opens. Deleting a child the page keeps showing (an address, a credential row) is the opposite case: invalidate plainly, so the list it stays on refetches.
- A read that costs the server more than one row per row shown (a rule preview evaluates the whole directory for every page) sets a `staleTime` and `refetchOnWindowFocus: false`; its key already changes when the thing it asks about is saved.
- A query for the signed-in account's own data carries `meta: { requiresSession: true }`, which is how clearing the session finds them all: `clearSessionQueries` cancels and removes by that marker instead of naming every key. A new session-scoped query needs the marker, or a sign-out leaves its data cached.
- A cursor-paged list is an infinite query, and its key belongs to that infinite query alone. Read it only through `useCursorList`; never pass a list factory's key to `fetchQuery`, `query`, `ensureQueryData`, `prefetchQuery`, `useQuery`, `useSuspenseQuery`, `setQueryData` or `getQueryData`. TanStack Query remembers that a key was built by an infinite observer, so a plain read of it returns `{ pages, pageParams }` or runs the paging behavior with options it does not have. `cursorListOptions` appends `cursorPagesMarker` to every list key so that no plain key — including one built from an administrator-chosen slug or Client ID — can equal it. A guard that needs to know whether a record is visible reads that record, not the list.

## Routing and guards

- Routes are files under `src/routes`; the tree is generated into `routeTree.gen.ts` and never edited by hand. A route file exports `Route` from `createFileRoute` and the page component lives under `src/pages`.
- Each route declares what it needs at the route: a `loader` for first-paint data, `pendingComponent` for the wait, `validateSearch` for search-string state. Reference `Route.useSearch()` from the page rather than reading the location.
- A failed or missing page takes one of three shapes, all in `RouteFeedback` (`src/components/custom`): the console's (`ConsoleRouteError`, `ConsoleRouteNotFound`), drawn in the page column under the header; the public card's (`PublicRouteError`, `PublicRouteNotFound`); and the whole window's (`AppRouteError`, `AppRouteNotFound`), on the public card alone, for when no layout is left to draw in.
- A page declares no `errorComponent`. TanStack gives a route its own `errorComponent` or the router's default and never its parent's, so the default, `RouteError`, reads `RouteLayoutContext` — which `ConsoleLayout` and `PublicLayout` provide around their `Outlet` — and draws the matching shape. The root route, `_protected` and `_public` declare `AppRouteError`, because their own failure leaves no layout to draw in. The not-found views are declared by the layouts (`_protected` and `_public`), and the router's default, `AppRouteNotFound`, takes an address neither claims; the console header names an address with no page as not found.
- Do not throw a bare `notFound()`: it goes to the nearest layout that declares a not-found view and replaces that whole layout. A page that must not exist throws `notFound({ routeId: rootRouteId })` for the whole-window view; a record that does not exist is the API's 404, drawn as a failure inside the layout.
- A failed page offers one way out, chosen by `describeRouteFailure` in `src/api/errors.ts`: "Try again" for a lost connection, a 5xx or a 429 (it resets the query error boundary and invalidates the router); "Reload" for a page that broke rather than a request that failed; "Sign in" for `no_session`; "Sign out" for `account_disabled`, where every other exit lands on the same refusal. Anything else leaves — for the console home, the sign-in page or the home page by shape — and the leave button is not drawn on the page it would lead to. A failure that carries its request adds "Details", the same dialog the toast opens.
- The signed-in area hangs off `_protected`, whose loader refuses an anonymous session: it clears the session queries and throws `redirect({ to: "/login", search: { return_to: location.href } })`, so signing in returns to the page that was asked for. Loaders may throw a redirect; catch blocks around `router.navigate`/`router.invalidate` treat it as the intended outcome rather than an error.
- The router reads the search string as strings only (`searchSerialization` in `src/app/search-params.ts`, spread into every `createRouter`, tests included): a value is the text the address carried, a repeated key is an array of its values, and writing one back takes only strings and arrays of strings. A search value stays a string in the route; a page that needs a number converts it where it reads it, as the audit log does with `account`.
- `validateSearch` is a Zod schema made only of the fields in `src/app/search-params.ts`: `searchText` and `searchChoice` for a value with a default, `optionalSearchText` for one that may be absent, and `rawSearchValue` for a value kept exactly as it came, a repeated key included. Each leaves the key optional in links and puts an invalid or repeated value back to its default rather than showing the error page.
- Tabs and other list selections live in the URL search string and nowhere else. A tabbed route's schema is `tabSearch(tabs)` from `src/pages/console/tabs.ts`, which falls back to the first tab for a missing, unknown or repeated value, and switching navigates with `replace: true` so the back button leaves the page instead of stepping through every tab.

## Public flows

- A page on the public card — sign-in, `/consent`, `/saml-consent`, `/enroll/$token`, `/welcome`, `/setup-signin`, `/federation/flow/$flow`, `/verify/vrchat/$proof`, `/pair`, `/sign-out`, `/error`, `/maintenance` — is a `PublicStep` (`src/components/custom`) inside the `PublicStage` that `PublicLayout` draws (a frame around the card, with a strip above it and a footer under it). `PublicStep` takes `title` (drawn by `PageHeading`, which takes focus as it appears and draws no ring), `titleKey` to remount the title when the step changes, `back` for the ghost back button, `description`, the body as children, `strip` (who is asking, as an `AppStrip`; portalled into the stage), `footer` (a choice or the decision, portalled under the card), `wide` for the wider card, and `actions` as a `PublicStep.Actions` — `layout="single"` stacks full-width buttons, `layout="decision"` is two equal columns with the answer that goes ahead on the right. A new public page composes it rather than drawing its own heading row; its buttons are `Button` with coss `variant`/`size` and `pending`.
- A public page that fails to load is `PublicRouteError`, through the router's default error view; the page declares no error component. A public button's failure is reported by the error toast, and the button comes back; a page that shows that failure itself (an alert or a field error) marks the write with `withInlineReport` (`meta.reportsInline`, a flag or a predicate for the errors it has a place for) and the toast stays silent for those, as `quiet` does for reads. `runWithSudo` takes `{ quiet: true }` for a caller that shows a failed sudo read itself. The consent pages share `ConsentRequest` (`src/pages/public/consent`), which owns the pending and disabled states of both answers and the switch to another account.
- Upstream providers are offered by `ProviderGrid` (`src/components/custom`) after an `OrSeparator` — one wide button, a two-column grid, or five cells with the rest in a searchable "More providers" popover — on the sign-in page's first step (followed by the "Sign in with your phone or another device" button, which opens `/pair` and shares the page's one-way-at-a-time lock through `onLeavingChange`) and on the enrollment page; the list comes from `publicFederationProvidersQueryOptions`, which carries no session marker because the list is public. A press is a full document load, and the buttons come back when the browser shows the page again from the back-forward cache. The passkey action on every public page is the shared `PasskeyButton`.
- A first password and authenticator on the public card is `PasswordTotpSetup` (`src/pages/public/enroll`), which the enrollment page and `/setup-signin` share, each with its own `submit`. The public pages call the API directly, never through `runWithSudo`: its prompt lives in the console. A `sudo_required` on `/setup-signin` leaves the step for the Security page.
- The enrollment preview, the prepared account on `/welcome` and a VRChat flow are read with `staleTime: 0` and without a refetch on focus, because the page's own write uses each of them up. Their loose fields are narrowed by `readEnrollmentPreview` (`src/api/enrollment.ts`) and `readFederationFlow` (`src/api/federation.ts`), which fail as `invalid-response` rather than guess.
- A loader never writes. Hover preloading runs loaders (`defaultPreload: "intent"`), so a loader that consumed a ticket or ended a session would do it for a link the reader only pointed at. A consent ticket is read with `GET`, which only looks at it; the decision is the page's `POST`.
- The first sign-in step's username field is `autocomplete="username webauthn"`, so the browser offers passkeys in its autofill. `usePasskeyAutofill` (`src/pages/Login.tsx`) keeps a conditional ceremony (`waitForPasskeyAutofill`, `src/api/auth.ts`) waiting while the step is open, where `isPasskeyAutofillAvailable` says the browser can. Waiting reports nothing — the reader pressed nothing — and a failure there is not retried; a picked passkey finishes through `passkeyAutofillMutationOptions` under the page's flow lock and fails the way the passkey button does, and autofill is offered again. The browser runs one ceremony at a time, so the passkey button pauses autofill before its own and resumes it afterwards. Both routes finish through `completePasskeyLogin`, which tells the password manager to drop a passkey the server answers `login_credential_unknown` for.
- The sign-in steps keep `return_to` and `admin` as `rawSearchValue`. `readReturnTo` (`src/api/auth.ts`) refuses a sign-in link whose `return_to` is repeated; `admin` counts whenever the key is there. The consent and error pages read their values with `optionalSearchText`, so a repeated value is treated as not given.
- `/pair` starts its pairing from the page, once, never from the loader, and reads its status every 2.5 seconds while it waits (`pairingStatusQueryOptions`, marked `quiet`, so a failed read is not a toast). A pairing that runs out, reads as expired or is gone when completed is shown expired with the offer of a new code; completing is an outcome (`pairingCompleteMutationOptions`), not an error. Once signed in, it offers a passkey through the same mutation as `/setup-signin`. The QR link opens `/devices?code=`, whose schema (`devicesSearch`) keeps only a whole code and opens the pairing dialog with it filled in; the lookup still waits for Continue.
- Maintenance is decided in the root route's `beforeLoad` by `maintenanceRedirect` (`src/app/maintenance-guard.ts`): while it is on, everyone but an administrator goes to `/maintenance`, except on that page and on a sign-in step whose search has an `admin` key. A request that fails with `maintenance_mode` is not a toast: the query client marks the cached config and calls `onMaintenance`, which navigates there.

## Forms

- Forms are TanStack Form through the hooks in `src/forms/use-app-form.ts`: `createFormHook` registers `FormField`, `OtpField`, `TextAreaField`, `AddressField`, `SwitchField`, `NumberField`, `ReadOnlyField`, the pickers (`AccountPicker`, `GroupPicker`, `IdentityProviderPicker`), `PrincipalSourceField` (which account fact a downstream application knows someone by), `Form`, `FormError` and `SubmitButton`, and pages call `useAppForm` rather than composing fields themselves. A field whose value is a list of rows is `RowsField` (`src/components/custom`). An editor whose rows draw their own column heading and a column for the remove button passes `removePlacement="inRow"`: the row receives its bound remove button and places it, and the header is drawn at the list's full width.
- An OIDC client's redirect and post-logout URIs are a row list, `UriList` (`src/components/custom`), built on the shared `AddressInput` (the same input sits behind `field.AddressField`): one input per address, checked by `uriListProblem`, with the error on the row it belongs to. Its scopes are `OidcScopesField`, a checkbox per scope the server knows. Both pages that edit an OIDC client use them.
- A short list of literal values — an identity provider's scopes and allowed email domains — is `TagListField` (`src/components/custom`): a tag per value with its own remove button and an input that adds one on Enter. The value is `{ tags, draft }`, so a submit can refuse text left in the input rather than dropping or adding it; values are kept exactly as typed, and what each list accepts is its `check` from `provider-validation.ts` (`src/pages/admin/identity-providers`), which the create and detail pages share. `src/forms/lines.ts` holds `LineProblem`, the numbered row problem `RowsField` reports.
- A change with a consequence past the save — the identifier a downstream application keys its users on, a token or OIDC scope removed, an identity provider's subject claim while accounts are linked through it — is confirmed when the form is saved, not when the control moves. While the form holds such a change the section's footer band states the consequence (`ConsequenceFooter`, in the `Section`'s `footer`, inside the form so its primary button is the submit) and the primary button names the action ("Remove scope and save"); submitting checks the form, keeps the checked request in the section's state and opens a `warning` `ConfirmDialog`, and the dialog sends it and closes once the write settles. Discard and cancelling leave the form as the reader had it, unsent. A section's footer appears only while something differs from what is saved, and a successful save resets the form to the record the server returned.
- Every create page ends its footer with `CancelLink` (`src/components/custom`): a link back to the list that is held (`aria-disabled`, out of the tab order, non-navigating) while the create is pending, so the page cannot be left mid-create and the element never changes.
- Field validation on blur, form validation on submit. Fields are disabled while the form submits, and a field's own server error is cleared as soon as the user edits it.
- Server errors reach the form through `src/forms/server-errors.ts`: a code or a `validation_failed` location maps to a field via a per-form `ServerFieldMap`, and anything unmapped becomes a form-level error. Do not print raw error codes; the message comes from `describeError`.
- `Form` is a plain `<form noValidate>`: validation is the form's own, not the browser's. It stops duplicate submits itself, and after a failed submit moves focus to the first invalid field that will take it — a field in a hidden layout will not — or else to the form's error summary. Keep `data-form-error-summary` on that summary so the focus target can be found.

## API layer

- Requests go through the single `client` in `src/api/client.ts` (openapi-fetch, same-origin credentials). It converts a failed response into an `ApiError` and an aborted request into an `AbortError`; a response with no body is not data, so reads return through `requireJsonData`.
- `src/api/errors.ts` is the only place that turns a failure into user-facing wording. Add a code to its table with translated text; keep `isCancellation` checks in catch paths so a cancelled request never surfaces as an error.
- An error message says what happened. It names the next step only when that step is a specific action — use the password instead, open a new link, choose again, wait a moment — and never a generic "try again": where a retry helps there is a button for it, and where it does not the sentence is wrong. Nor does it report an outcome such as "the list has been refreshed". Error wording on pages follows the same rule, so a failed page load and a failed button can share one line.
- `src/api/queries.ts` and `src/api/mutations.ts` hold query and mutation options; pages do not build request options inline. Generated declarations come from `mise run ci:api-types`; hand-written requests the generator does not cover belong in `src/api/raw-admin-paths.ts`. A path both files declare is merged method by method (`client.ts`): the generated entry spells the methods it does not document as `never`, so intersecting the two whole path objects drops the write, and dropping the whole generated entry loses the read's parameters.
- A write is a whole-record replacement on most of this API — an OIDC or SAML application, a forward-auth application, an identity provider. Omitting a field is not "leave it alone": it resets it. The request bodies are therefore built in `src/api/update-bodies.ts` from the saved record plus the fields the form edited, one function per resource, and a page never assembles one by hand. Each has a unit test asserting that the reset-on-omission fields are carried.
- The server narrows some fields loosely — a provider's `config` arrives as `unknown`, a SAML `attributeMap` as `unknown`, `mode` and `protocol` as plain strings. `src/api/federation.ts` reads them into the exact shapes the console renders and returns nothing for a value it cannot read, rather than casting at the call site.

## Console structure

- The signed-in pages share one shell, `ConsoleLayout`, built on the coss `Sidebar` (`variant="inset"`) with `SidebarProvider`: `ConsoleIdentity` (the instance's icon and name) at the top, a navigation list that names a section and its icon once, the account footer (`ConsoleAccount`: a menu with Profile, Security and sign-out), and, in the inset panel, a sticky header with the sidebar trigger and a breadcrumb that shows which section you are in. Below `md` the same list opens in the sidebar's sheet; `CloseSheetOnNavigate` closes it when the address changes. Each entry is a TanStack `Link` rendered through `SidebarMenuButton` — a real `href`, so it opens in a new tab, and the router marks the current page with `aria-current`. The management entries sit under three headings, directory, applications and system, and a heading with no entry the account may see is left out whole, so a member who manages only applications sees that one group. Add a section by adding one entry to the list in `ConsoleLayout`, with its `group` if it is a management page, not by drawing a nav of your own.
- A page draws its own single `h1` through `PageHeader` (`src/components/custom`): the title, an optional line saying what the page is for and actions on the trailing edge from `sm`. The shell's header only names the section in view with a breadcrumb, which is not a heading, and it reads the same section table the sidebar does, so a label is written once.
- Member pages (account, security, devices, connected applications) sit in `PageBody`, one measured column (`max-w-3xl`) that holds the header and the sections, in `main`, which is also a container context (`@container`). Every block keeps to that measure at every width, tables included; nothing bleeds back into the gutters.
- A block on a console page is a `Section` (a coss `Frame`): a muted band with the title, an optional `icon` and `description` and the block's primary `action`, then the content on a white panel. An `ItemList` or `DataTable` placed in a section is that section's panel, so a section never holds a card inside a card. Sections stack in one column at every width; below `sm` the header stacks the action under the description. Where a card holds a single line of controls beside a small graphic — an icon next to its upload control — the two sit in a row from the wide breakpoint and stack below it.
- The instance's name, icon and sign-in page appearance come from `useInstanceBranding` (`src/components/custom/instance-branding.ts`), which reads `GET /config` — the effective values, including an override saved in the settings. The root route loads `/config` before the first paint. The sidebar, the console header, the public toolbar (the sidebar and the toolbar through `InstanceIdentity`), the public layout's background and surfaces, and `document.title` all read the hook; the shell's `<title>` carries the effective name from the server, which fills it per request, so the tab is titled correctly even before the script runs. Image URLs — the icon and every uploaded sign-in image — carry the ETag as `?v=`, so a replaced image is a new URL rather than a cached one, and a write to any of these settings invalidates `["public", "config"]`.
- The public layout draws the appearance through `PublicScene` (`src/components/custom`), which `PublicLayout` fills with the route and the sign-in page editor's preview fills with a sample step, so the two cannot drift. The scene is `LoginBackdrop` (colour, gradient preset, Bing's picture, or the Unsplash batch or the uploaded images, each at random or as a carousel by its own settings), the `AppToolbar` on two capsules, the `PublicStage` the page sits on and `WallpaperCredit` (Bing's caption or the credit of the Unsplash photo on screen, which follows the carousel; in the bottom corner away from the card from `lg` and under the card below it). `useLoginBackground` picks the pictures for the source and holds the rotation so the credit and the photo change together. `src/components/custom/login-appearance/surface-style.ts` draws a surface: an opaque one is `bg-card`; a translucent one is the `surface-glass` rule in `src/styles/index.css` at `--card-alpha`, blurred when the setting says so; `cardSurfaceStyle` adds `surface-glass-controls` on a translucent card, which gives the controls drawn on it see-through fills at half of `--card-alpha`, so they are clearer than the card. The public card and the translucent capsules take it. A Bing or Unsplash picture is read with `loginWallpaperQueryOptions`, marked `quiet`: until it arrives, or if it cannot, the page keeps its own background and says nothing. The card's position and the credit's corner come from `card-position.ts`, which applies from `lg`. A theme the settings force is `publicThemeAtom` (`ThemeSelect.tsx`), written only by `PublicLayout` in a layout effect while it is mounted and cleared when it goes; `AppEnvironment` writes it on `<html>` (the `dark` class and `data-theme`) in place of `themeAtom`, before paint, so the console's theme is never changed and no frame shows the other theme. `AppToolbar` drops the theme control while one is forced.
- The sign-in page editor (`/admin/settings/sign-in-page`, `src/pages/admin/settings/sign-in-page`) previews the page in `SignInPreview`: an inert same-origin iframe (`PreviewDocument`) that copies the console's stylesheets and portals the shared `PublicScene` into its own document, with the real first sign-in step (`PasswordPage`, under `LoginPreviewContext`) on the draft's settings. The frame is laid out at 1280×800 (desktop) or 390×844 (phone) and scaled into its box, so breakpoints, the theme and the card's position mean what they will for visitors; nothing in it can be used. A Bing or Unsplash picture is read for the draft's region or keyword a moment after it stops changing.
- The management area has two gates, and a new page belongs under the one that matches who may open it. `_protected.admin` admits an administrator *or* an account assigned to manage at least one downstream application, because the server lets a delegated manager read and change the applications it was assigned; `_protected.admin._admin` (pathless, so the URLs do not change) admits administrators alone, and holds the user directory, user groups, invitations, identity providers, logs, settings and the landing page. The three application sections hang off the outer gate and each checks its own kind. The sidebar entry that leads to a page is hidden on the same question the route asks, and `useManagementSections` in `ConsoleLayout` is where that is decided for an application section: an administrator sees them all, anyone else sees only the kinds `managedApplicationsQueryOptions` reports. A hidden entry is never the only thing keeping someone out.
- A page is a tab strip or a stack of sections, and the choice is how much of it belongs on screen at once. Tabs suit a few independent views that each want the full measure; a stack suits a handful of short blocks a reader takes in together. `/security`, `/profile`, `/admin/settings`, and every record detail page — a user, an identity provider, a downstream application — are stacks: their parts are short, and a reader checks several of them in one visit or changes two in one sitting. A stack shows every block without a control to work through, and mounts all of them on arrival, so every section's reads start at once. Use tabs when the sections are long, and a stack when the page is a short inventory.
- A sectioned page is a column of `Section` (`src/components/custom`), one per block: the page file owns the order and the gaps and nothing else, and each panel draws its own `Section`. A section's title then stays beside the button it names, and the button's handler stays with the state it reads; a parent that passes an action in as a `ReactNode` separates one concern into two files. `Security.tsx` is the example: a `PageBody` holding the page header and the four panels.
- `Section` draws the heading as an `h2`, one level under the page's `h1`, inside the frame's header band with the action on the trailing edge; the panel below holds only the content.
- A section keeps its heading while it loads. Every panel that reads server data wraps its content in `AsyncSection` (`src/components/custom/Section.tsx`), which passes `title`, `icon` and `description` to the `Section` it draws while waiting or failed, and gives the suspense and error boundary plus a retry. Inside it the panel reads with `useSuspenseQuery(quietQuery(...))`: the boundary is where a failed read is told, so the query is marked quiet and no toast repeats it. A lookup that only decorates the panel (provider names, a menu's choices) is a quiet `useQuery` that falls back silently.
- `AsyncSection` repeats the title, icon and description the panel draws in its own `Section`, so the heading is on screen from the first frame; share them through small components so the two copies cannot drift. A boundary that is not a section, such as a panel under a tab strip, passes no title: the tab strip already names it.
- A tabbed page keeps the selected tab in the URL (see Routing), never wraps a tab label, and lines the tab strip up with the card below it. Tabs take the width of their labels rather than equal columns, so a five-tab strip still fits the measure.
- Nothing on a console page is collapsed. A tab that carries many independent actions is an `ItemList` with one row per action — its name, one line saying what it does, and its button — so every action is visible at once. An action that needs input opens that input in a dialog; one that needs none runs from the row, behind a `ConfirmDialog` when it cannot be undone. A list of sign-in factors writes each factor's state in its row, and a missing one is established by the section's primary action, in a dialog, rather than by a form drawn in place.
- Lists come in two shapes, chosen by how they are read:
  - The management directory (users, user groups, invitations) is a `DataTable`. It runs to many rows and pages, and an admin compares one column down the rows — role, state, last sign-in — which is what column alignment is for. Keep its columns to what fits the measure; put row actions in the pinned column as icon buttons.
  - Everything the signed-in account owns (passkeys, sessions, identities, tokens, connected applications) and the per-account lists on an admin's user page are an `ItemList`. Those hold a handful of records read one at a time, so each row names the record, carries a muted line of details that name themselves ("Added …", "Last used …") instead of leaning on column headers, and keeps its actions at the trailing edge.
- List pages follow the same shape: the page's action first at the top left, followed by its search and filters, then the list over the page's query, with `TableEmptyState` for the empty case. Collect input in a dialog or a popover (the identity filter), not in a panel that expands under the toolbar.
- A list that is the page's whole subject stays on the page background: no `ItemList` title, with the action row and any notice above it in a plain `flex flex-col gap-4` column. The console header already names it. Devices is the example: the signed-in devices are the list, and signing in a new one — the pairing code, then the approval of the device it finds — happens in a dialog opened from the action above it rather than in a form on the page. A list that is one block among several — the four lists on an admin's Access tab — takes an `ItemList` `title`, which draws the heading inside the frame.
- Panels on the same page go through the same `useAppForm` fields and the same list, empty state and dialog shapes; a panel that draws its own list, form or button row is the outlier to fix.

## Tables and lists

- Console tables come from `DataTable`, given one column definition per column (id, header, cell, `align`, `pinned`), a `rowId`, the rows, and an `empty` node. Cells and headers never wrap; a table wider than its column scrolls sideways instead of clipping. A time the reader asks "how long ago?" of — last used, last signed in, started, authorized, a pairing request — is a `RelativeTime`: "3 days ago" on the row, the exact date and time in its tooltip. A date the reader plans around, such as when a token or an invitation expires, shows the day only. A time that does not help anyone act, such as when an identity was linked or when a session will expire, is left off the row. The audit log is the one exception: its time is written to the second in the reader's locale (`tabular-nums`), because audit entries are compared by the moment against other logs.
- A row with more to show than fits its columns passes `expandedRow` to `DataTable`: the first column carries the toggle, and the detail is a child row with one cell spanning every column, held at the scroll area's leading edge and no wider than it. A row whose `expandedRow` returns `null` has no toggle. Which rows are open is the table's own state, not the URL's.
- A trailing action column is marked `pinned` and renders through `TableActionCell` / `TableActionColumn`, which stick to the container's trailing edge so row actions stay reachable while the other columns scroll under them. The pinned cell paints its own opaque background; leave that to the component. Its leading-edge shadow shows only while there are columns left to scroll under it: `table-pinned` in `src/styles/index.css` runs it off the scroll container's scroll timeline, in CSS alone. A browser without scroll timelines (Firefox today) shows no shadow.
- A detail page for an application — OIDC, SAML or forward-auth — for an identity provider, for an account and for the instance settings is `AppDetailLayout` around its sections (`src/components/custom`). The layout draws the `ObjectHeader` (icon, the `h1`, status badges, a copyable identifier, short facts and the page's actions) or, on the settings page, a `PageHeader`; the sections in one column, and from `lg` an `OutlineRail` beside them: one in-page link per `Section`, the danger section last, an unsaved dot on a section with edits, and the page's identifying facts (an issuer, an Entity ID) under it. Below `lg` the rail is left out and the facts move under the header. Every `Section` registers itself with the layout, which is also what the floating unsaved bar is drawn from; while any section is dirty the layout reserves room under the last row, so the bar never covers it. The application kinds share the sections that mean the same thing: `AppAccessSection` is the access policy (the restriction switch, the group list and its order of evaluation), `AppManagersSection` the accounts allowed to manage it, and `EntityIconControl` the icon, inside an Appearance section. The Managers section is drawn for an administrator only, because the endpoint behind it is administrator-only; a delegated manager gets `AppManagerNote` under the header and no Managers section.
- A user group's page is a sibling shape, not an `AppDetailLayout`: the `ObjectHeader`, then a main column of sections (details, then the rule builder or the decisions list, the danger section last) and, from `lg`, a sticky 300px side column of read-only context in place of the `OutlineRail`: for a rule group the matches frame and the "check an account" frame, for a manual group the decisions count, then "Used by". Below `lg` the side column's context reads before the danger section, not after it. Nothing in the side column is editable, and the column sticks only while it fits the viewport, and a taller one scrolls with the page, because a scroll area inside a sticky column has no visible edge and hides its last block. The group page shares `UnsavedBar` and `useUnsavedReserve` with `AppDetailLayout`, so the floating unsaved bar never covers the last row on either.
- A section whose save does more than store a value — removing a scope, changing the NameID or the user identifier — ends in `ConsequenceFooter`: what the save will do, Discard, and a primary button named for the action ("Remove scope and save"), so the reader meets the consequence at the button they press. A read-only value the reader pastes elsewhere is `CopyValue` (a field with a copy button) or, inline in a header or the rail, `CopyableValue`; both report through `CopyStatus`, so "Copied" and the refused-clipboard warning read the same everywhere. A long identifier in a header breaks after its slashes rather than inside a segment, and the copy button stays beside the first line. A SAML signing certificate's state is written by `CertificateText`, in words and with its date, never by colour alone.
- A management table does not carry a status column of the ordinary state. A column of "Enabled / Enabled / Disabled / Enabled" is mostly the word "Enabled": it costs a column out of the measure and the reader still has to scan it. The row's identity goes through `EntityCell` (`src/components/custom`), which draws the `EntityAvatar`, the name linking to the record, and the monospace identifier under it. `EntityCell`'s `marks` takes badges that follow the name for a fact the row has to say in words (a provider's `NotReadyChip`). Beside the chip the list gives the reason, the short form of the detail page's `notReadyReason` sentence (`notReadyReason(provider, true)`), so the two cannot disagree. A row that is switched off *recedes* — `EntityCell`'s `dimmed` lowers the icon and the name a little — and carries a small "Disabled" badge beside the name, because a settled decision should not shout but a screen reader and a reader who cannot tell opacities apart still need the word; the recession is decoration on top of a fact, never the only record of it. The identifier under the name keeps its full muted colour, since it is what a reader scans for in a switched-off row. The state that *does* get a mark is the one an operator has to act on: a provider that is not ready cannot be enabled, so it carries `NotReadyChip`. Restricted access is a `Lock` after the name rather than a chip, because it says what a row *is* rather than something that happened to it. Any list of users, user groups, identity providers or downstream applications uses it.
- The four federation lists — identity providers, OIDC, SAML and forward-auth applications — take their shared cells from `ListCells` (`src/components/custom`): `NotReadyChip`, `CodeValue` (a monospace value with the whole of it in a tooltip, for a value the table will clip), `RedirectCell`, `LinkedAccountsCell` and `PrincipalSourceCell`. A cell two of them need belongs there rather than in one page's column list. The three application lists also share their column tracks (`APP_DATA_COLUMN` on each of the two data columns, the application column flexible), so they put their columns on the same lines and the columns stay put as rows load or run out; a monospace value is an identifier in the muted colour at one size, and a word is sans in the foreground colour. Each list leads with one diagnostic column that answers "is this row set up the way I expect", because the useful fact differs per kind — a redirect count, a certificate expiry, a linked-account count — and a generic column would be empty for someone.
- While rows are still loading, `DataTable` stands in with placeholder rows — one `Skeleton` per column, three rows deep, which reads as chrome rather than as data and holds the table's height so it does not jump when the first page lands. `ItemList` waits with `ListSkeleton` (`src/components/custom`) inside its frame. Do not branch on loading inside cell or row renderers.
- `ListSkeleton` is the one wait shape for a list of records: an icon-sized block and two lines per row, drawn with the coss `Skeleton`. `SectionPending` in `Section` and the panels that read with `useQuery` draw it, so a block keeps its shape whether or not the rows have arrived, and the wait and the result cannot disagree about a row's height. It is `aria-hidden` on purpose: a set of placeholder bars has nothing to announce, and the list's own label is what a reader is waiting on. A `Spinner` stays right where the wait is a *process* rather than a shape — the route-level pending, the in-flight lookup in `EntityPicker`, and the work a `Button` reports through `pending`.
- `ItemList` is one CSS grid in a coss `Frame` panel with a rule between rows, and every row is a subgrid of it, so the icon, badge, meta and actions columns are as wide as the widest cell and line up down the list whatever the rows hold; `columns={{ actions: true }}` keeps a floor under the actions column for a list whose rows may all have none. `ItemListRow` takes `icon`, `title`, `badges` (chips beside the name), `badge` and `meta` (the list-wide state and short-fact columns; below `sm` they follow the name and its details as one line), `details`, `actions`, `link` for a row that opens the record, `dimmed`, `stackActions` and `children` for a row's own note. A row that is a description with one labelled action — a setting, a danger row — sets `stackActions`, and below `sm` the action drops under the text at its natural width, left-aligned, as a `SettingRow`'s control does; rows of icon buttons or a menu keep their actions beside the name. A row's menu is `RowMenu`. `footer` sits under the last row, for an action over the whole list.
- An action the account cannot take right now stays visible and disabled, and the reason is written in the row or description beside it (`aria-describedby` points at it), not in a tooltip that a keyboard or touch screen never sees.
- An irreversible row action goes through a confirmation that names what it removes. Every confirmation is `ConfirmDialog` (`src/components/custom`), never a hand-built `AlertDialog`: it draws a status icon beside the heading and decides the button order and the pending state once. `danger` is for what removes something for good; `warning` for a change of state that can be undone, such as turning on maintenance mode or activating a signing key. It does not close itself on confirm; the caller does, when the write settles or at once.

## Components and surfaces

- Use the wrappers in `src/components/custom` when one exists (the list below is what exists): `AddressInput`/`field.AddressField`, `AppAccessSection`, `AppDetailLayout`, `AppManagersSection`, `AsyncSection`, `Button`, `ChoiceTile`, `ConfirmDialog`, `ConsequenceFooter`, `DangerZone`/`DangerZoneFrame`, `EntityPicker`, `CopyableValue`, `CopyValue`, `EntityAvatar`, `EntityCell`, `EntityIconControl`, `ImageDropTile`, `ImageUploadControl`, `InstanceIdentity`, `InlineFailure`, `ItemList`, `ObjectHeader`, `OutlineRail`, `PageBody`, `PageHeader`, `PrincipalSourceField`, `RelativeTime`, `RowMenu`, `RowsField`, `Section`, `SegmentedControl`, `UnsavedBar`/`useUnsavedReserve`, `SurfaceAlert`, `SecretReveal`/`SecretRevealDialog`/`SecretRevealStep`, `TableActionCell`, `TableEmptyState`, `TokenAccessSummary`/`TokenAccessBadge`, `FormField`, `OtpField`, `OptionSelectField`, `TagListField`, `PublicStep`/`PublicStage`/`PublicScene`, `ProviderGrid`, `PasskeyButton`, `DataTable`, `ListSkeleton`, `CancelLink`, `JsonBlock`.
- Choosing, replacing and removing one image — the instance icon, an entity's icon — is `ImageUploadControl`: the hidden file input behind an upload button that becomes "Replace" once there is one, the remove button, the size and type check against the endpoint's own list before anything is sent, and the rejection or the caller's failure as a `SurfaceAlert`. The preview stays with the caller. A grid of pictures with the upload as its last tile is drawn from `ChoiceTile` (a choice drawn as a tile, `compact` for an icon over a name, `media` for a picture over a name) and `ImageDropTile` (the dashed tile that takes chosen or dropped files): the sign-in page's background sources and its list of up to ten images (`LoginImagesControl` in `src/pages/admin/settings`), and the profile page's avatar gallery (`AvatarPanel` in `src/pages/profile`). Both image grids check files with `rejectImage` and the size cap, and the gallery reports a rejected file with `ImageRejectedAlert`. The wrappers exist so one place decides the pending spinner, the surface treatment, or the pinned cell, and every call site stays consistent.
- Every button in the app is `Button` from `src/components/custom/Button.tsx`, including `form.SubmitButton`. Mark work in flight with `pending` and let the wrapper draw the spinner: a labelled button keeps its text beside it, an icon-only button swaps the icon for it. Do not put a `Spinner` inside a button, and do not swap the label yourself to signal pending.
- Pending work is shown on the control that started it, in the component the user is looking at; a page-level toast is for outcomes, not for progress.
- A write that succeeds says so in a success toast; nothing on the console succeeds silently. The mutation carries its line as `meta.success`, taken from `src/api/success-messages.ts`, and the query client raises the toast, so it still arrives after the dialog that started the write has closed. A write that answers with something to read — recovery codes, a token, a registration or invitation link — shows that instead, and a page does not print its own "saved" sentence beside the form. A direct request that is not a mutation calls `notifySuccess` itself.
- Notices use `SurfaceAlert` (a coss `Alert` with `AlertTitle`, and `AlertDescription` only for supplementary text). A page-level notice — outside any card — is coss's own `Alert`.
- A write whose failure the page draws itself passes its mutation options through `withInlineReport(options, true)` and keeps the failure with `useInlineFailure` (`report` ignores a cancellation, `clear` on retry), drawn by `InlineFailure`; a read the boundary tells is `quietQuery`. Each failure is reported once, never as both an alert and a toast.
- One-time codes go into `OtpField`, never a free-text box: digits by default, a passed `pattern`/`inputMode` for letter-bearing codes such as the pairing code, in the coss OTP slots with a separator where the code is shown that way elsewhere. The slots keep coss's own size and start at the field's leading edge; they do not stretch to fill a card or a dialog, and they shrink only when the column is narrower than the code.
- A dialog is `@/components/ui/dialog`: `DialogHeader` for the title, `DialogPanel` for the content that scrolls, `DialogFooter` for the actions, cancel on the left and the one that finishes on the right. The form element spans body and footer, so a long body scrolls under a footer that stays in place.
- `SudoDialog` is the console's only prompt to confirm who is signed in, and a write reaches it through `runWithSudo`, never a dialog of its own. Its methods sit on one screen, each with its own button, so it has no footer. It replays the refused write once after verifying: when that replay fails, the dialog closes and the error reaches the caller's own error handling, the same as a write made while the window was already open.
- A secret the server will not show again — recovery codes, a token's plaintext — is revealed in `SecretRevealDialog` for one step of a section, `SecretRevealStep` as the last step of a dialog the caller owns, and `SecretReveal` page-wide only when the flow is finished either way. The reveal gates its continue action on the saved confirmation, hides the dialog's close button until then, warns before leaving the page, and hides the canvas or field it cannot draw yet rather than unmounting it.
- A component that draws from asynchronous data keeps the element mounted and skips the value it does not have yet. Unmounting on an empty value loses the ref, and the later real value has nothing left to draw on.

## Layout and chrome

- The page's share of the viewport comes from the `--app-viewport-height`, `--app-sticky-offset` and gutter properties in `src/styles/index.css`. Full-height regions, sticky headers and rails use those properties instead of `100dvh` and `top-0`, so a development panel docked at an edge never hides the page; an undocked page reads the defaults. See Devtools for who writes them.
- Keep `html` `position: static`. Base UI places a popup against the viewport when the containing block is `html`; a positioned `html` makes the browser measure from the whole document, and every tooltip on a long page lands far below what it describes.
- A sticky region is pinned by an ancestor that does not scroll. An `overflow-hidden` wrapper is a scroll container, so sticking the aside inside it pins it to a box that never scrolls; the transition wrapper sticks and the aside fills it.
- A side rail ends with its own footer — the account row — inside a column that can shrink (`min-h-0`), otherwise a short viewport pushes the footer out of the rail and clips it. The coss `Sidebar` already lays out its header, content and footer this way; keep a new rail section inside its `SidebarContent`/`SidebarFooter`.
- The console shell is three tonal layers, from the outside in: the chrome, the inset panel, and the blocks. The sidebar is the chrome and takes `--sidebar`; `SidebarInset` is the page and takes `--background`; every `Frame` panel is the card surface. That is the whole of the shell's depth — keep it to tokens rather than adding borders or shadows to separate the layers. The header is sticky and translucent (`bg-background/80`, blurred) and closes with a `border-b` because content scrolls *under* it, which is a fact about the edge rather than a fourth layer.
- The rail is the coss `Sidebar`; its selected entry is the sidebar's own accent state, which keeps the medium weight and the icon pairing. An unselected entry keeps the component's regular weight and muted icon. Do not restyle entries per screen; the colour the rail takes from the product appears only in the selection.
- The rail lines up on one edge: the instance avatar, every entry's icon, the group headings and the account avatar.
- The rail already names the instance, so the header names only the section in view. An eyebrow repeating the instance above the heading would say the same thing twice and take the size the heading needs; `ConsoleIdentity` is where the instance belongs.

## Translations

- A message's placeholders are named in the source, never positional: take the value into a local (`const count = …`) and write `{count}`, not `{provider.linkedAccountCount}`, which Lingui extracts as `{0}`. Both catalogs carry the same names; `src/locales/catalog-placeholders.test.ts` fails when a translation drops a value, invents one, or leaves a `#` outside a plural. A translation may drop an argument its source uses only to choose a plural branch, since Chinese rarely inflects there.
- `pnpm run i18n:extract` adds new ids to both catalogs but keeps the English text of an id that already exists. When a message's source text changes, change its `en` entry to match, or the console keeps showing the old words to English readers.

## Devtools (development only)

- The TanStack Devtools shell and the API dock are mounted behind `import.meta.env.DEV` from `main.tsx`, beside the API mock, so none of it ships in the production bundle. Nothing under `src/devtools` may be imported by app code.
- The dock watches the shell's panel through the DOM and writes the page's share of the viewport on `<html>`. It is a watch rather than a devtools plugin because a plugin renders only while its own pane is open, and the page has to make room for whichever panel is open.
- Mock fixtures live with the mock, not in the components that read them, and the mock owns whole verbs: while reads are mocked every GET is answered, writes only when "Override writes" is on. The panel's rows edit one config object; a write updates that object so later reads agree with it.
- The mock covers the management area as well as the account pages, and the panel is the switchboard for a walkthrough: the **Session** role decides whether the management section appears in the sidebar and whether its pages answer or redirect home, and the **Management** counts decide how many accounts, user groups, invitations, audit events and signing keys exist. The account directory and the audit log page by cursor, so their counts go well above what a single page holds — a walkthrough has to be able to reach the second page. The account directory honours `q` (username or display name, before it pages), and every application has accounts 2 and 3 as its managers, so the assign dialog shows both an already-assigned and a disabled candidate (account 4). The audit log honours the server's filters, and the signing keys move through their states as the handlers move them.
- The **Instance** section drives `/config`: the name override, maintenance mode, whether a custom icon exists, the sign-in page's background source, how many sign-in images are uploaded (0–10) and whether an Unsplash key is saved. The mock answers `/config` with built-in placeholder images as `data:` URLs rather than `/branding/*`, which is not an API request it can intercept, and both wallpaper endpoints with `data:` pictures — Bing's one with a sample caption, a batch of five Unsplash photos in different hues, each credited to its own photographer — so no walkthrough reaches Bing or Unsplash. A write to the settings moves the same fields, so the sidebar, the header and the sign-in page follow a save. The rest of the appearance is set by saving it on the settings page, or through the URL (`?mock.instance.loginAppearance.card.translucent=1`). An access key starting with `bad` is refused as Unsplash would refuse it.
- The **Public flows** group drives the consent pages: a first-time or a more-access consent, the scopes the application asks for (one of them its own, `wiki:write`), whether it has a logo and policies, whether the ticket is still good, and how many attributes a SAML service receives. It also sets up the enrollment link any token previews (its intent, a fixed username, whether a password and authenticator are allowed, up to three providers, an invitation bound to the first, whether the invite requires a local sign-in method, whether it already carries a verified identity, an expired link), the account on `/welcome` (whether it has a picture; whether a local sign-in is offered; an expired sign-in) the VRChat flow (its intent and step, a username asked for, a proof not in the bio yet), and the pairing `/pair` starts (how many status reads before it is approved, 0 for never, and how long its code lasts; starting one is a write, so it needs **Override writes**). A passkey enrollment fails as `mock_unmocked`, like every passkey ceremony. The maintenance page and its guard are walked through with **Instance → Maintenance mode** and the **Session** role. A change of session in the panel moves a signed-in reader off the sign-in steps and an anonymous one out of the console; it leaves the other public pages to their own loaders.
- The **Avatar** group sets up the profile page's gallery: whether the account has uploaded a picture, how many pictures from providers are stored (0–3, named after the connected identities' providers), and whether the account has picked one before. `GET /me/avatar` and the session's picture are read from the same fields, so the sidebar follows the page. With **Override writes** on, an upload is shown at once only while the account has never picked, a choice records that it has (a source that is not stored is refused as `avatar_source_unavailable`), and removing the upload in use falls back to the first provider's picture or none. The picture in use is also `?mock.avatar.active=user|none|upstream:provider-N`.
- The mock keeps the account it is signed in as in step with the directory's first row: editing that account's profile or role moves both, so the session the console reads and the record the admin list reads never disagree.
- A request with no fixture fails as `mock_unmocked` instead of reaching the server, so a page never draws half fabricated data and half real data. Passkey ceremonies fail that way, since a fabricated challenge cannot be answered.
- Mocked responses wait the configured delay before they answer, so the pending states a page draws while waiting stay visible during development. Keep that wait in the mock, and keep the panel's list sizes and delay capped by the exported maxima.
- The master switch returns to off after a reload, while the data edits, including the writes switch, persist: a console left serving fabricated data across reloads would hide the server it is being developed against.
- The mock also reads the address bar, so a walkthrough can set a screen up without the panel: `?mock` turns it on, and any `mock.<path>` parameter both turns it on and writes the field that path names in the config — `?mock.admin.oidcApps=7&mock.session.role=member`. The vocabulary is the config's own paths rather than a second set of names, values are clamped the way the panel clamps them, and an unknown path or an unreadable value is ignored rather than creating a field nothing reads. `applyMockQuery` (`src/devtools/mock/query.ts`) is the whole rule; it runs once at install and again on every navigation, which is what clears the reload reset above for a scripted pass.

- A monospace console field is `FormField` with `compactValue`: its value is 16px below `sm`, so iOS does not zoom on focus, and 13px from `sm`. Public pages leave it off and keep the input's own sizes (`lg`).
- A secret is set from its own row (the Steam key, the OIDC client secret, the operator session), as a status badge beside the action that replaces it. It is never part of the danger zone, which only disables and deletes.
- The quiet latest-test summary (`latestConnectionTestQueryOptions`) is read once and feeds both the Diagnostics badge and the claim table's "what the test saw" column. It holds no claim values, so any administrator may read it from any browser.
